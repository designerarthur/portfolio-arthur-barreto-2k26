        Four decisions, each with a reason

        1. A persistent sidebar puts size first, the facet that decides if a shoe is even an option. Shoppers narrow the list without losing their place.

        2. A four-column grid with a corrected hierarchy: image, name, then price. Badges and wishlist stay secondary, so cards are easy to scan and compare.

        3. The active item changes color and gains a left border, so people always know where they are.

        4. Category navigation starts from what people do, like running, football or training, in a minimalist layout with soft pastel tones from the brand.

                Optimizing workflow with MCP

                How I connect Figma to an AI assistant without burning tokens, and what it changed in my day.

                ABArthur BarretoUX/CRO designer · Oct 2026 · 5 min read

                What MCP actually is

                Model Context Protocol is a standard way for an AI assistant to talk to your tools. Instead of pasting screenshots and describing a frame in words, the assistant asks Figma directly: which layers exist, how they are laid out, which tokens they use. You stay in the conversation, and the tool answers with structure.

                Why designers should care

                Most of the friction between design and code is translation. Someone reads a frame, then retypes it as spacing values, colors and component names. With MCP the assistant reads the same source you do, so there is one file to trust and far less copy and paste between tools.

                It also makes repetitive production work cheap: renaming layers, auditing spacing against a scale, filling every state of a component. The boring parts get faster, and the time goes back to decisions.

                My token-efficient setup

                Every call returns data, and data costs tokens. A few habits keep sessions fast and cheap:

                1. Fetch by node ID, never the whole file. Ask for the frame you are working on and nothing around it.
                2. Request only the fields you need. If the task is layout and text, skip fills, effects and history.
                3. Skip screenshots when structure is enough. A flag like excludeScreenshot keeps the response light.
                4. Load fonts once. Pre-load every variant in a single call before touching any text.
                5. Batch your changes. Collect every edit, then apply them together instead of iterating after each tweak.
                // one frame, only what the task needs
getDesignContext({
  nodeId: "12:48",
  excludeScreenshot: true
})

// fonts once, edits once
await loadFonts(["Regular", "Medium", "Semibold"])
apply(allChanges)

                A sketch of the pattern, not an exact API.

                Small, precise context beats a full dump every time.

                Where it helps, and where it does not

                It shines on production: variants, states, spec tables, token audits and turning a frame into a first draft of code. It does not decide what to build, it has no taste, and it cannot sign off on accessibility. I review every output the way I would review a junior teammate's work.

                Takeaway

                Start with one small task, like auditing spacing against your 8pt scale. Keep the context tight, batch the edits, and let the assistant do the repetitive part while you keep the decisions.

                Flex grid for responsive layouts

                One small rule set that adapts anywhere, so you stop redrawing the same layout at every breakpoint.

                ABArthur BarretoUX/CRO designer · Oct 2026 · 4 min read

                The problem with fixed columns

                A 12-column layout at 1440 pixels looks great. Then you redraw it at 768, again at 375, and the three versions slowly drift apart. Every change in the design means three edits, and a fourth when a new device size shows up.

                The flex approach

                Instead of fixing the number of columns, give each card an ideal width and let the container decide how many fit. Items grow, shrink and wrap on their own.

                .grid {
  display: flex;
  flex-wrap: wrap;
  gap: 16px;
}
.card {
  /* ideal width of 280px, free to grow or wrap */
  flex: 1 1 280px;
  max-width: 480px;
}

                There is no breakpoint in that code. At 1280 pixels you get four cards per row, at 768 you get two, and at 375 you get one.

                Rules I follow

                1. Spacing comes from the 8pt scale. Gaps of 8, 16, 24 and 32, never anything in between.
                2. One gap token for rows and columns. Equal gutters keep the grid reading as one system.
                3. Set a minimum and a maximum. Cards should never get too thin to read or too wide to scan.
                4. Decide what happens to the last row. Orphans stretch if you let them grow, so cap the width or accept it on purpose.
                5. Let the outer margin step up. 16 on phones, 24 on tablets, 32 on desktop.

                Designing it in Figma

                Use auto layout with wrapping, set a minimum and maximum width on the cards, and build one component. Then resize the parent frame and check three widths: 375, 768 and 1280. Write the intent next to the component, for example "ideal width 280, minimum 240", so the handoff describes behavior and not just one screenshot.

                Flex or CSS grid?

                They solve different problems. Flex is great for a flow of similar cards that should wrap naturally. CSS grid is better when rows and columns have to align in two dimensions, like dashboards and full page layouts. I reach for flex first for content lists, and for grid when alignment across rows matters.

                Design the rules, not every screen size.
                Takeaway

                Pick an ideal card width, a gap from your scale, and a minimum and maximum. Test at three widths and let the layout do the rest.

                The impact of AI on design

                Where AI meets creativity: what it speeds up, and what still needs a designer.

                ABArthur BarretoUX/CRO designer · Oct 2026 · 6 min read

                What it is good at

                AI is strongest where the work is wide and repetitive. It can explore many directions in minutes, produce variations of a layout, draft first-pass copy, summarize research notes and fill in the states of a component. Those are real hours back in the week.

                What it cannot do

                It does not know your users, your business constraints or your brand history unless you tell it, and even then it is guessing. It cannot own accessibility, and it will not push back when a request is wrong. Those responsibilities stay with the designer.

                AI widens the set of options. Design is still the act of choosing.

                How my role shifts

                I spend less time producing and more time framing and judging. The work moves toward defining the problem clearly, setting constraints, and deciding which output is good enough to ship. Taste becomes the bottleneck, and also the advantage.

                Rules I use

                1. Write the constraint before the prompt. Audience, brand, grid and tokens go in first, so the output starts close to the system.
                2. Treat every output as a draft. It goes through the same checks as human work: contrast, spacing, states and copy.
                3. Keep real users in the loop. A faster draft is not evidence. Test with people and look at behavior.
                4. Log the decision. Write down why this option won and the others did not, so the reasoning survives the tool.
                Takeaway

                Use AI to go wider and faster, then use your judgement to go deeper. The designers who benefit most are the ones who can say clearly what good looks like.

                Innovating with design

                Turning ideas into products: the small loop I use to get from a sketch to something people can use.

                ABArthur BarretoUX/CRO designer · Oct 2026 · 5 min read

                Innovation is shipped learning

                Ideas are cheap. The value shows up when real people use something and we learn from what they do. That is why I treat innovation less as a spark and more as a loop that I can run again and again.

                The loop

                1. Idea. What problem are we solving, and for whom? If I cannot say it in one sentence, the idea is not ready.
                2. Wireframe. What is the smallest version that can answer the question? Rough boxes are enough to test the flow.
                3. Product. Polish it, ship it, and watch behavior. What did we learn, and what do we change next?
                A good idea is a hypothesis with a deadline.

                Working like a CRO designer

                Conversion work taught me to write the hypothesis first: we believe this change will help this behavior, and we will know because of this signal. Change one thing at a time, measure behavior instead of opinions, keep the wins and document the losses. The losses are where most of the learning is.

                Keep it small

                Small bets are easier to ship and easier to throw away. Constraints help too: a fixed grid, a short deadline and a single metric focus the work. I prototype early, in Figma or in code, and ship thin slices instead of waiting for the whole thing to be ready.

                Takeaway

                Write the question, build the smallest thing that can answer it, and let behavior decide what comes next.
